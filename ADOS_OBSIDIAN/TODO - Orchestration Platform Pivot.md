## Core substrate (Section 11, step 1 — before any new domain agent) — all 4 items resolved 2026-08-04

[In plain terms: this section is about the foundational plumbing (message queues, a security rules engine, a proper login system) the whole bigger platform needs before we can add more business departments — HR, Finance, Legal, etc. — to it. As of 2026-08-04, every item below has a real, evidence-based answer: one was actually built (the event schema upgrade), and three were deliberately *not* built yet, each with a specific, written reason and a specific trigger for when to revisit — not skipped, not silently deferred.]

- [x] **Done 2026-08-03**: event schema comparison against `agentic-org`'s `core/schemas/events.py` (`PlatformEvent`) and `messages.py` (`TaskAssignment`/`TaskResult`), field by field. Three concrete gaps found in `contracts/event_envelope.py`:
  1. `incident_id` is a **required** field on the shared envelope — hardcodes "everything is about a manufacturing incident," which breaks the moment an HR/Legal/Finance event has no "incident" concept at all. Should become a generic `correlation_id`.

## Bug found AND fixed: /events/stream never delivered a live event (found + fixed 2026-08-04)

- [x] Root cause confirmed by direct repro (a standalone async script, not guesswork): `backend/app/routers/events_stream.py`'s loop wrapped the **shared bus generator's own** `stream_iter.__anext__()` in `asyncio.wait_for(..., timeout=0.5)`. `InMemoryEventBus.stream()` has a `try/finally` that deregisters its subscriber queue on any exception — including `CancelledError`. Every 0.5s tick with no traffic (the common case), `wait_for`'s timeout cancels that pending await, which propagates a `CancelledError` through the generator, runs its `finally`, and **permanently closes the generator** after the very first tick. Every later `__anext__()` call then raises `StopAsyncIteration` immediately, which the route read as "stream ended" — explaining "ping, then clean close" exactly, and why it happened every single time, not intermittently.
  [In plain terms: the code was accidentally sabotaging its own listener. Every half-second it checked "any new events yet?", and if the answer was "not yet," the way it asked the question actually broke the connection to the event source — like hanging up a phone call because the other person hasn't spoken in half a second, then wondering why they never call back.]
- [x] **Fix**: stopped applying the timeout directly to the shared bus generator. Instead, a small background task continuously pumps events from the bus generator into a local, connection-private `asyncio.Queue`, and the route's timeout/disconnect-polling loop now waits on *that* local queue instead. `asyncio.Queue.get()` is safe to cancel — a timed-out wait just leaves it unconsumed, no side effects — unlike the bus generator's own await. The destructive cancel-and-unsubscribe now only happens once, deliberately, during real cleanup (client disconnect or `max_events` reached), which is exactly when it should happen.
  [In plain terms: instead of asking the fragile question every half-second, there's now a dedicated background helper that stays permanently and calmly connected to the event source, and just quietly hands off anything new to a separate, safe-to-check mailbox. The half-second timeout now only checks that mailbox, which can be checked and re-checked with no risk of breaking anything.]
- [x] **Verified as a real fix, not just a plausible one**: wrote a new regression test (`tests/test_events_stream_router.py::test_events_stream_delivers_a_live_published_event`) that opens the stream, waits past the old 0.5s failure window, then publishes a real event and asserts it's actually delivered — not just the ping. Confirmed it **fails** against the old code (reproduces the exact bug) and **passes** against the new code, by temporarily reverting just the loop logic and re-running. Full suite: 196/196 passing (195 previous + this new one). Also confirmed the fix doesn't depend on the Kafka work at all — it's in the route's polling loop, identical regardless of backend.
  [In plain terms: before calling this done, the fix was proven two ways — first by writing a test that actually watches for a real live event (the old tests never did this, they only checked the opening heartbeat), then by checking that test genuinely fails on the old broken code and passes on the fixed code, not just that it happens to pass.]
